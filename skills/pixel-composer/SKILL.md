# Pixel Composer 제작 가이드

의도가 담긴 아트는 유저의 정확한 정의, 그 정의의 언어화, 레퍼런스 없이는 나오지 않는다. 그래서 **질문 → 제작 → 유저 피드백**은 생략하지 않는 과정이다.

이 문서는 강제 절차가 아니라 가이드라인이다. 노드와 툴은 선택지일 뿐 정답이 아니다. 절차의 순서도 예시이므로, 필요하면 언제든 앞 단계로 돌아간다.

## 하지 않는 것
- **인터뷰 전에 만들기.** 필수 빈칸과 레퍼런스 없이 제작을 시작하지 않는다. "답이 없으면 기본값으로 진행합니다"라고 말하고 만들어 버리지 않는다.
  - 급하다는 요청에도 질문은 한다. 대신 질문 수를 줄이고, 줄일 수 없는 것만 묻는다.
- **요청에 없는 요소 추가.** 레퍼런스와 확정 사항에 없는 레이어·효과·장식(화면 번쩍임, 잔류 효과, 외곽선 색 등)은 넣기 전에 묻는다.
- **AI로 대충 뽑은 티가 나는 결과.**
  - 픽셀 크기가 섞임, 반 픽셀
  - 의도하지 않은 안티앨리어싱, 반투명 가장자리
  - 색이 너무 많음, 거의 같은 색이 여럿
  - 떠 있는 픽셀, 노이즈 같은 디더가 전체에 깔림
  - 실제 크기에서 실루엣이 안 읽힘
  - 빛 방향이 제각각
  - 크기에 비해 디테일이 너무 많음

  **레퍼런스의 디테일 밀도에 맞추고, 덜어낼 수 있으면 덜어낸다.**

| 이런 생각이 들면 | 실제로는 |
|---|---|
| "급하니까 가정하고 일단 만들자" | 틀린 가정으로 만든 시안은 처음부터 다시 만든다. 질문 2~3개가 더 빠르다 |
| "기본값을 알려줬으니 확인받은 셈" | 유저가 답하지 않은 기본값은 확정이 아니다 |
| "이걸 넣으면 더 멋있겠다" | 요청에 없는 요소는 스타일 이탈이다. 넣고 싶으면 먼저 제안한다 |
| "check_sheet를 통과했으니 됐다" | 숫자 검사는 위생만 본다. 실제 크기 1배와 레퍼런스를 나란히 놓고 직접 본다 |
| "이 기능은 없을 테니 다른 방법으로" | `references/capabilities.md`를 먼저 본다. 생성기·뼈대·외곽선·팔레트 노드가 이미 있다 |

## 절차

### 1. 인터뷰
첫 답장은 질문이다. 아래 중 유저 메시지와 첨부로 답이 안 되는 것만 묻는다.

**공통 필수**
- **용도:** 화면 어디에, 언제 보이나.
- **실제 크기:** px 단위. 기준(캐릭터 키 등) 대비 배율. 픽셀 퍼펙트 여부.
- **레퍼런스:** 이미지나 영상. 좋은 점과 싫은 점.
- **팔레트·기존 에셋:** 게임 팔레트, 같은 세트의 기존 작업물.
- **실제 화면:** 게임 스크린샷 또는 배경. 밝기와 대비를 판단하는 데 쓴다.
- **출력 규격:** 파일 형식, 프레임 크기, fps, 시트 배치, 저장 위치.

**작업별 항목**은 해당 참고 문서에 있다.
- 이펙트: `references/vfx.md`
- 아이콘: `references/icon.md`
- 타일: `references/tileset.md`
- 캐릭터: `references/character-rig.md`

### 2. 확정 사항 메모
- 답을 받으면 크기·스타일·팔레트·타이밍·레퍼런스 요점을 5~10줄 메모로 정리해 유저에게 보여준다.
- 이후 시안을 보여줄 때마다 메모와 대조한 결과를 함께 말한다.

### 3. 빠른 시안
- 실루엣·타이밍·스케일이 보이는 거친 버전을 먼저 만든다. 세부를 다듬는 건 그다음이다.
- 노드는 `references/capabilities.md`에서 고른다. 입력 번호는 `describe_node`로 확인하고 추측하지 않는다.
- 작업 방식:
  - **반복과 재현이 필요한 작업:** Python 빌드 스크립트로 한다. `pixel_composer_mcp.graph`(`new_project`, `Graph`, `emitter`, `switch`, `curve`, `gradient`, `color`)를 쓰고, 모든 값을 스크립트에 둔다.
    - 실행: `uv run --with git+https://github.com/3Hoo/pixel-composer-mcp python build.py`
    - 완성 예시: 리포의 `examples/elemental-rise`
  - **조회, 작은 수정, 실험:** MCP 툴로 한다.
    - `inspect_project`, `set_input`, `set_keyframes`, `add_node`, `connect`, `export`
- 경로에는 공백을 쓰지 않는다. 겪은 함정은 `references/pitfalls.md`에 있다.

### 4. 검사
- **숫자 검사:** `check_sheet(path, style, frame_w, frame_h, ...)`
  - 픽셀 스타일에서 보는 것: 하드 알파, 색 수(`max_colors`), 떠도는 색(어느 프레임인지 알려줌), 외톨이 픽셀 수, 픽셀 격자(`pixel_scale`).
  - 이펙트 규칙(프레임 수, 지면, 최고 높이, 가장자리)은 인자로 줄 때만 검사한다.
- **눈 검사:** `check_sheet`가 만드는 `_contact.png`와 함께 아래를 본다.
  - 실제 크기 1배
  - 게임 배경 위
  - 레퍼런스 옆에 나란히
- **움직임:** GIF나 프레임 나열로 확인한다. 직접 확인하지 못한 것은 확인하지 못했다고 말한다.

### 5. 보여주기와 피드백
- **보여줄 것:** 결과 파일, 1배와 확대 미리보기, 메모 대조 결과, 조정할 수 있는 항목.
- **피드백 반영:** "더 무겁게", "탁하다" 같은 피드백은 원인을 살펴서 형태·커브·색·타이밍 같은 구체적 변경으로 옮긴다.
- **반복:** 유저가 승인할 때까지 3~5단계를 반복한다.

### 6. 개선 루프
작업을 마친 뒤, 이 스킬이 틀렸거나 부족했던 점을 유저에게 정리해 알린다. 새 함정, 검증된 노드, 더 나은 노드 조합 같은 것들이다.
